# Как строить экраны для e-ink дисплея

Правила для любого экрана, который сервер рисует и отдаёт на `/frame`.
Они выведены из тестов на реальном дисплее: экран, свёрстанный «как для обычного монитора», на e-ink становится нечитаемым.

## Дисплей

| Параметр | Значение | Что из этого следует |
|---|---|---|
| Разрешение | 800×480 | Кадр ровно 800×480, ни пикселем больше |
| Диагональ | 7.5" → ~124 dpi | 1px ≈ 0.2 мм. Текст 12px — это буквы высотой ~1.7 мм |
| Цвета | чёрный, белый, красный | **Полутонов нет.** Серый, прозрачность, сглаживание — всё станет одним из трёх цветов |
| Обновление | полное, ~28 с, экран мигает | Перерисовываем только когда картинка реально изменилась |

## Как картинка попадает на экран

```
HTML-шаблон ──► Chromium (скриншот 800×480, со сглаживанием)
            ──► EinkPalette: каждый пиксель → чёрный / белый / красный
            ──► PNG на /frame (ETag = хеш итоговой картинки)
            ──► клиент на Pi: делит на чёрный и красный слои → дисплей
```

Перевод в 3 цвета (`eink-dashboard-server/.../frame/EinkPalette.java`):

- **красный**, если `R − max(G, B) ≥ 50`, то есть по оттенку;
- **чёрный**, если яркость `< 160`;
- иначе **белый**.

PNG с `/frame` — это уже итоговая картинка: что видно в нём, то будет на дисплее.

## Главная проблема: сглаживание

Браузер рисует края букв и линий полупрозрачными пикселями. На мониторе это выглядит гладко, а на дисплее каждый такой пиксель становится либо цветом, либо белым.
У толстых крупных элементов хватает «плотных» пикселей, и форма сохраняется. У тонкого мелкого текста почти все пиксели — край, и после перевода от буквы остаются обрывки.

Отсюда все правила ниже: **элементы должны быть достаточно толстыми, чтобы пережить перевод в 3 цвета.**

## Правила

### Цвет

- Только три цвета: чёрный `#000000`, белый `#FFFFFF`, красный (например, `#C1200A`).
- **Никакой `opacity`**, `rgba` с прозрачностью, серого текста, теней, градиентов, фоновых картинок и фотографий.
  Серый не станет «бледным»: он превратится в рваный чёрный или пропадёт целиком.
- Второстепенный текст выделяем **размером, весом, регистром или расположением**, а не бледностью.
- Красный — для акцентов (текущая температура, «сегодня», предупреждения), а не для основного текста.

### Текст

| Что | Минимум | Вес |
|---|---|---|
| Основной текст | 13px | 400 |
| Второстепенный (даты, подписи) | 12px | 400–500 |
| Подписи заглавными с разрядкой | 12px | 600 |
| Красный текст | 14px | 500 |
| Цифры декоративным шрифтом с засечками | 18px | обычный |

- **Вес 300 и тоньше не используем.** На тесте 11px/300 («Ощущается», «Влажность») стал нечитаемым.
- Шрифты с волосяными засечками (Playfair, Didot и т. п.) — только крупно, от 24px.
- `letter-spacing` у мелкого текста держим небольшим (до ~0.1em), иначе буквы рассыпаются.

### Шрифты

- **Шрифт обязан поддерживать кириллицу.** Если в шрифте её нет, браузер молча подставит системный шрифт, и в одной строке смешаются два шрифта.
  Проверка: на Google Fonts в поле *Language* у шрифта должна быть Cyrillic.
  Пример: DM Sans и DM Serif Display кириллицы **не** имеют.
- Шрифт без кириллицы допустим только для цифр и латиницы (так в тестовом экране сделаны крупные цифры DM Serif Display, а «мм» набрано другим шрифтом).
- Выбирать шрифт, сделанный для экранов с низким разрешением: широкие буквы, большая высота строчных, открытые формы.
- Результаты сравнения на тестовом экране (рендер на macOS, после перевода в 3 цвета):

  | Шрифт | Результат |
  |---|---|
  | **DejaVu Sans** | лучший: ровные ножки, `°` остаётся колечком. Используется в тестовом экране, **проверен на дисплее** |
  | Golos Text | читается, но ножки разной толщины, `°` в 13px слипается в квадрат |
  | PT Sans | хуже: узкий, буквы рваные |

- DejaVu Sans — системный шрифт, он должен быть установлен на сервере: macOS `brew install --cask font-dejavu`, Linux `fonts-dejavu-core`.
- Шрифты с Google Fonts требуют интернета на сервере. Для продакшена лучше хранить файлы шрифтов в ресурсах сервера.

### Сглаживание при рендере

- Почему буквы получаются «кривыми»: браузер рисует их не по пиксельной сетке, а перевод в 3 цвета округляет каждый край. Ножки одной толщины получаются то 1px, то 2px.
- **На macOS сглаживание не отключать** (`-webkit-font-smoothing: none`): macOS не применяет хинтинг, буквы становятся тоньше, между ними появляются дыры, тонкие `+` пропадают. Проверено, хуже текущего варианта.
- На Linux (продакшен) Chromium рисует шрифты через FreeType, который умеет хинтинг: ножки подгоняются под сетку. Рендер без сглаживания с полным хинтингом (fontconfig: `antialias=false`, `hintstyle=hintfull`) может дать заметно более ровный текст. **Не проверено**, проверить при переезде на Linux.

### Линии и иконки

- Линии от 1px, лучше 2px для важных разделителей. Ставим на целые пиксели, без дробных координат и `transform: scale`.
- Толщина штриха иконки **в итоговом размере** — от 2px. Если SVG с `viewBox="0 0 100 100"` рисуется в 28px, штрих в нём должен быть ≥ 7.
- Иконки от 28px. Мелкие детали (точки, тонкие лучи) в мелкой иконке пропадают.
- Красная заливка с чёрной обводкой рядом — нормально, но между ними не должно быть «полосок» в 1px.

### Вёрстка

- Страница = кадр: `body` без отступов, корневой блок ровно 800×480, фон белый.
- Никаких анимаций, переходов и таймеров: скриншот делается один раз после загрузки страницы.
- Оставляем запас места: текст после замены шрифта или реальных данных не должен вылезать за блок. Длинные значения проверяем отдельно (например, `−25°`, «Переменная облачность»).

### Содержимое и частота обновлений

- Каждое изменение картинки — это ~28 секунд перерисовки с миганием. Не выводим то, что меняется каждую минуту без необходимости (секунды, «обновлено N минут назад»).
- `ETag` считается от итоговой картинки, поэтому одинаковые данные не перерисовывают экран.

## Как проверять экран

1. Посмотреть PNG с сервера: `curl -o frame.png http://<server>:8080/frame`. Это уже 3-цветная итоговая картинка.
2. Увеличить в 3–4 раза **без сглаживания** (nearest neighbor) и проверить мелкий текст, `+`, `°`, точки, тонкие линии.
3. Без дисплея: `python3 client.py --once --dry-run out.png` на Pi сохраняет ровно то, что ушло бы на экран.
4. Финальная проверка — на самом дисплее.

Чек-лист перед выводом нового экрана:

- [ ] нет `opacity`, серого, теней, градиентов;
- [ ] нет текста мельче 12px и тоньше 400;
- [ ] у всех шрифтов есть кириллица (или ими набраны только цифры);
- [ ] иконки от 28px, штрихи от 2px в итоговом размере;
- [ ] на увеличенном PNG с `/frame` читается каждый символ.
